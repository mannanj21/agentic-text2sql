# Security Report

Generated by `scripts/generate_security_report.py` from the committed validator corpus.

## Threat model and controls

The system treats user questions, database metadata, and returned cell values as
untrusted. Controls are layered: input guardrails bound request size and flag
obvious attacks; SQL validation permits one safe `SELECT`/`WITH` AST only;
target databases use a read-only role, read-only transaction, timeout, and row
cap; and platform controls encrypt credentials, enforce ownership, reject
unsafe resolved hosts, and rate-limit requests. Credentials are decrypted only
inside introspection and execution modules and never stored in graph state,
prompts, traces, or API output.

Residual risks include a misconfigured target read-only role, a compromised
hosted model/provider, and natural-language answer quality. The validator is
defense in depth, not a replacement for database permissions.

## Database boundary defense

The integration suite bypasses the validator through the test-only internal value
constructor and proves that PostgreSQL still blocks five representative threats:
write DML, data-modifying CTEs, `SELECT INTO`, `pg_sleep` (statement timeout),
and `pg_read_file` (role privileges). The executor additionally forces every
transaction to read-only mode.

Some controls are intentionally **validator-only defenses**: the demo readonly
role may select `customers.email`; PostgreSQL allows harmless multi-`SELECT`
input; and several PostgreSQL functions (for example `current_setting`,
`set_config`, advisory locks, and a non-existent backend PID passed to
`pg_terminate_backend`) are callable by the readonly role. Metadata policy and
the deterministic single-statement/function rules therefore prevent these
values or effects from reaching execution. The full corpus-boundary integration
test classifies every blocked corpus case as database-blocked or validator-only.

## Prompt-injection defense

Input heuristics are deliberately treated as weak speed bumps. Structural
controls carry the safety claim: generated SQL must pass the single-statement,
read-only validator before the executor accepts its opaque `ValidatedSQL`
value; the target role and read-only transaction remain a second boundary.
Security tests use a FakeLLM that obeys a question-level attack by producing
`DROP TABLE` and prove the executor is never called. Result-cell text is placed
only inside `<QUERY_RESULT>` delimiters; a hostile cell may influence a bad
natural-language answer, but the answer node has no database execution tool.

## SSRF and credentials

Connection setup resolves every hostname answer, rejects loopback/private,
link-local, and metadata-service addresses by default, and pins the connection
to the validated address to prevent DNS rebinding. `ALLOW_PRIVATE_HOSTS=true`
exists only for the local Docker demo. Credentials are encrypted at rest with
the environment-provided Fernet key; rotating that key invalidates stored
connection credentials and must be planned as a migration.
